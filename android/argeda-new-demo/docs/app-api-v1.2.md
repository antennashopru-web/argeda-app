# API для приложения ARGEDA — дополнения к версии 1.2

Задание для треда «Работа на сервере argeda.ru». Основа — `docs/app-api-v1.md`, здесь только новое. Приложение 1.2 уже умеет всё описанное ниже и включит это само, как только сервер начнёт отдавать данные. До этого оно работает как сейчас.

Порядок работы как обычно: сначала копия и показ, выкладка только по «выкладывай», бэкап базы перед выкладкой.

## Что уже проверено и работает

- `POST /orders` в тестовом режиме: заказ оформляется из приложения, ответ 201.
- `/repair/services?model=Samsung SM-A015F` → «Samsung Galaxy A01»: коды Samsung распознаются.
- Координаты пункта на Лермонтова отдаются в `/config`.

## 1. Ошибки, которые нужно поправить

1. **Xiaomi распознаётся неверно.** `model=Xiaomi Redmi Note 8 Pro` → «Redmi Note 6 Pro», `model=Xiaomi Redmi Note 8` → «Redmi Note 5». Без слова «Xiaomi» распознаётся верно. Приложение пока отрезает «Xiaomi» само, но поправить нужно на сервере. Проверьте и другие марки: производитель + модель, как их отдаёт Android (`Build.MANUFACTURER` + `Build.MODEL`).
2. **Наличие расходится.** Товар `cmqk3zae1004w11n5mu4ycxap` в `/catalog/home` и в карточке «today», а в `/orders/quote` — «preorder». Источник наличия должен быть один.
3. **`/orders/quote` молча выкидывает несуществующий `product_id`.** Нужна строка в `warnings` с `code: "not_found"` и этим `product_id`.
4. **`GET /repair/bookings`** отдаёт `status: "NEW"` заглавными (POST отдаёт `"new"`) и не отдаёт `model`. Нужны строчные статусы везде и поле `model`.
5. **Одинаковые заказы.** Второй `POST /orders` с тем же телефоном и составом, но другим `Idempotency-Key`, вернул тот же заказ A-415. Если это защита от повторов — ок, напишите правило (окно по времени). Если нет — разберитесь.
6. **Статус и шаги заказа расходятся.** Тестовый заказ приходит со `status: "ready"`, но в `steps` шаг «Готов к выдаче» стоит `done: false`, а `pickup_code` пустой. То есть шапка говорит «готов», а линия прогресса и QR — «ещё не готов». Нужно: когда `status` меняется, обновлять `done` у всех пройденных шагов и класть `at` (время этапа); при `status: "ready"` выдавать `pickup_code` для QR. Приложение теперь само приводит линию в соответствие со `status`, но источник истины должен быть на сервере, иначе настоящий «готов» не покажет QR-код выдачи.

## 2. Шесть пунктов выдачи

В приложении 1.2 покупатель выбирает пункт из шести — как на argeda.ru/punkty. Мастерская — только на Лермонтова, 2. Список пунктов пока зашит в приложение, координаты есть только у Лермонтова (из `pickup`).

1. **Отдавайте пункты в `/config`:**

```json
"pickup_points": [
  {"id": "lermontova", "name": "на Лермонтова", "address": "Пушкино, ул. Лермонтова, 2", "hours": "10:00–20:00", "lat": 56.013733, "lon": 37.841808, "workshop": true},
  {"id": "chekhova", "name": "на Чехова", "address": "Пушкино, ул. Чехова, 33", "hours": "10:00–20:00", "lat": 0, "lon": 0}
]
```

   - `id` — постоянный: приложение запоминает выбор покупателя по нему.
   - Нужны настоящие координаты каждого пункта.
   - Как только `pickup_points` появится, приложение возьмёт список оттуда: можно добавлять и закрывать пункты без обновления.
2. **Принимайте пункт в заказе.** Приложение уже шлёт в `POST /orders` и `/orders/quote` поле `delivery: {"type": "pickup", "point_id": "chekhova", "address": "Пушкино, ул. Чехова, 33"}`. Сейчас сервер его игнорирует, поэтому приложение дублирует пункт в комментарии («Пункт выдачи: ул. Чехова, 33. …»). Нужно:
   - сохранять пункт в заказе и показывать его в CRM, админке и уведомлениях;
   - возвращать `delivery.point_id` и `delivery.address` в ответах `/orders` и `/orders/{id}`.

   Когда сделаете — напишите, и дублирование в комментарии уберём.
3. **Наличие по пунктам.** На сайте есть «Завтра в пункте», а `availability` в API одна на все пункты. Если товар лежит в одном пункте, а в другой едет, нужен параметр `point_id` у `/catalog/products` и `/orders/quote`: тогда «Сегодня в пункте» будет правдой для выбранного пункта.

## 3. Фильтры в списке товаров

`GET /catalog/products` — новые параметры (вместе с `category`, `q`, `sort`):

| Параметр | Что делает |
|---|---|
| `in_stock=1` | только то, что можно забрать сегодня (`availability = "today"`) |
| `price_min`, `price_max` | цена в рублях, включительно |
| `brand` | бренд из характеристик, точное совпадение |

Когда всё готово, включите в `/config`: `"features": {"filters": true}`. Пока флага нет, приложение показывает только фильтр «Для моего телефона». Он уже работает через `q`.

Сейчас сервер эти параметры игнорирует. Флаг включайте, только когда заработают все три.

## 4. Баннеры на главной

Сейчас `/catalog/home → banners` — это товары, первым стоит коммутатор «под заказ». Приложение 1.2 такие баннеры больше не показывает. Вместо них — свои пять баннеров: разбит экран, аккумулятор, пульты, деталь по фото, самовывоз. Тексты и цены в них берутся из `/repair/services` и `/catalog/categories`.

Чтобы менять баннеры без обновления приложения, отдавайте новый формат:

```json
"banners": [
  {
    "title": "Разбит экран?",
    "subtitle": "Замена от 40 минут · от 1 500 ₽",
    "kicker": "Ремонт",
    "image": "https://argeda.ru/app/banners/screen.jpg",
    "action": {"type": "repair", "value": "screen"}
  }
]
```

- `action.type`: `repair` (value — проблема: screen, battery, port, water, camera, other), `category` (id раздела), `product` (id товара), `search` (запрос), `photo`, `pickup`, `url` (только https).
- Картинка 960×408, тёмная слева — текст ложится на левые 60%. Готовые фоны лежат в `android/argeda-new-demo/app/src/main/assets/img/banners/`. Исходники и макеты — в Figma, файл «ARGEDA — баннеры приложения».
- Баннеры с сервера встают перед встроенными. Старый формат (без `action`) приложение пропускает.
- Не ставьте в баннеры товары под заказ.

## 5. Подсказки поиска

`GET /catalog/suggest?q=акк` →

```json
{"queries": ["аккумулятор samsung a01", "аккумулятор iphone 11"],
 "categories": [{"id": "…", "name": "Аккумуляторы", "count": 1015}]}
```

- Подсказки — из реальных запросов покупателей на сайте и в приложении, с результатами > 0.
- До 6 запросов и 3 разделов, ответ быстрее 150 мс.
- Пока приложение подсказывает только разделы, по своему списку категорий.

## 6. Доверие: рейтинг, отзывы, гарантия

Только настоящие данные. Если чего-то нет — не отдавайте поле, и приложение его не покажет.

- `/config`:
  - `"repair_warranty": "90 дней"` — гарантия на ремонт, как в договоре мастерской;
  - `"rating": {"value": 4.9, "count": 312, "source": "Яндекс Картах", "url": "https://yandex.ru/maps/…"}` — рейтинг мастерской.
- `GET /catalog/products/{id}`: `"rating": {"value": 4.8, "count": 27}` — когда появятся отзывы о товарах. Отзыв можно просить после выдачи заказа, через SMS со ссылкой.
- То же поле `rating` в элементах списка `GET /catalog/products` (`items[]`) — звёзды и оценка показываются прямо в карточках каталога, поиска и лент.
- `GET /catalog/products/{id}/reviews?page=N` — список отзывов: `{ "items": [{ "author": "Алексей", "value": 5, "date": "2026-10-10", "text": "…", "photos": [] }], "total": 27, "summary": { "value": 4.8, "count": 27, "breakdown": {"5": 20, "4": 5, "3": 1, "2": 0, "1": 1} } }`. Отзывы — только от подтверждённых покупателей (после выдачи заказа), с модерацией. Экран отзовов в приложении уже готов и возьмёт эти поля.
- Важно: **в приложении рейтинг и отзывы сейчас демонстрационные и показываются только в тестовой сборке** (помечены «демо»). В боевой сборке их нет, пока сервер не отдаёт настоящие оценки. Нельзя показывать покупателям выдуманные отзывы — ждём ваши данные.

## 6a. Фильтры: бренд и фасеты

Фильтры цены, наличия и сортировка уже работают (`price_min`, `price_max`, `in_stock=1`, `sort=`) — проверено на живом API, спасибо. Чего не хватает для фильтра «как на ВБ»:
- **Бренд.** В товарах нет поля `brand`, фасетов тоже нет. Добавьте `"brand": "Samsung"` в товар и поддержите `brand=Samsung` (можно несколько через запятую).
- **Фасеты в ответе списка.** В `GET /catalog/products` добавьте `"facets": { "brand": [{"value":"Samsung","count":1203}, …], "price": {"min":35,"max":769990} }` — чтобы приложение показывало реальные бренды и диапазон цены в фильтрах, а не угадывало.

## 7. Курьер

- Цену курьера приложение уже берёт из `/orders/quote` (сейчас 140 ₽).
- Добавьте срок в `/config`: `"courier": {"eta": "Сегодня до 21:00, если заказать до 18:00"}`. Текст — как реально работает доставка.

## 8. Что можно сделать позже

- **Сортировка «популярные» идёт по алфавиту** (подряд «Apollo», «ARESA», «ACTIVE…»). Нужна настоящая популярность: продажи и просмотры за 30 дней, сначала то, что есть сегодня. Пока лента «Рекомендуем» на главной берёт товары из случайных страниц разделов.
- `GET /catalog/feed?page=N` — лента для главной: популярное и новое из разных разделов, без повторов между страницами, с учётом модели телефона (`model=`).

- `GET /catalog/for-model?model=Samsung SM-A015F` — товары для модели телефона: запчасти, стёкла, чехлы, зарядки, сначала с наличием сегодня. Сейчас приложение ищет через `q=A015F`: это работает, но захватывает похожие модели (A01 Core).
- `GET /catalog/products/{id}/related` — «С этим покупают» по реальным заказам.
- Push-уведомления о статусе заказа — после ключей RuStore (этап 4).
